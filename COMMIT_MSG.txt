feat: API-key auth, multivariate flags, and a Redis-backed evaluate path

Three changes that close the largest gaps in the service, plus the tests and
CI to keep them closed.

Auth (ripcord/auth.py)
  Every endpoint except /health and /metrics now requires a scoped API key.
  Keys are `rpc_<key_id>_<secret>`: only key_id is stored in plaintext (indexed,
  so verification is one lookup), the secret half as a SHA-256 digest compared
  with hmac.compare_digest. A fast digest is correct here — these secrets carry
  256 bits of entropy, so a slow KDF would only add latency to every request.

  Scopes are `flags:read`, `flags:write`, `sdk` and `admin`. Separating `sdk`
  from `flags:write` is the point: the credential shipped inside an application
  binary can read the ruleset but cannot flip a flag. Flag changes are now
  attributed to the key that made them, so the audit log stops saying "system".

  /stream additionally accepts ?api_key= because browser EventSource cannot set
  headers. That exception is opt-in per route and tested to not leak elsewhere.

Multivariate flags (ripcord/engine.py)
  Weighted variants carrying arbitrary JSON. A flag with no variants is still a
  plain boolean flag — same table, same engine, no second code path.

  Variant choice is hashed on a different salt than rollout inclusion. Without
  that, everyone admitted by a 20% rollout would sit in the lowest buckets and
  land in the first variant, silently ruining the experiment. Variants are laid
  out in key order rather than storage order, so reordering them in the UI does
  not reshuffle users. The engine stays total (it never raises) so an SDK
  evaluating a stale ruleset can't fail on the hot path; validation lives at
  the API boundary instead.

/evaluate served from Redis
  The ruleset cache is now a hash keyed by flag, so /evaluate is a single HGET
  rather than a Postgres query per call, and invalidation is per-flag instead of
  dumping the whole ruleset. A reserved __ruleset__ field distinguishes "cache
  is cold" from "there are no flags". Redis being unreachable degrades to the
  database rather than failing the request.

  Measured with k6, 50 VUs / 20s, two runs per configuration:
    database:  321 / 357 req/s   p95 379/349ms   p99 541/533ms
    redis:   1366 / 1445 req/s   p95  76/ 71ms   p99  87/ 81ms
  ~4.1x throughput, ~6.4x lower p99. (2-vCPU container with everything
  co-located, so absolute numbers are contention-bound; the ratio is the claim.)

Also
  - Dashboard: key entry and verification, auth on every request, variant
    editing, rule-to-variant pinning, and an API keys management page.
  - scripts/e2e.py: 37 checks against a real running stack — real uvicorn, a
    schema built by Alembic rather than create_all, real HTTP and a real SSE
    socket. CI runs it against `docker compose up`.
  - CI: Postgres/Redis service containers, a migration up/down/up check, the
    dashboard type-check and build, and the e2e job.
  - Tests: 66 -> 144. The whole pre-existing suite now runs authenticated.
